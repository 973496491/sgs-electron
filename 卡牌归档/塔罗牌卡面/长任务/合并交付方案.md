# 塔罗牌卡面合并交付方案

制定日期：2026-10-21。本文是离线素材交付设计，尚未执行整批合并，也没有修改游戏加载链。单卡生成状态以 `runtime/state.json`、单卡记录及实际文件为准，不能把本方案或队列存在视为生成完成。

## 交付结论

采用 **四份花色图集 + 精确资源花色映射 + 全部独立 PNG + 原始回退页**。四份图集均保持原 atlas 的坐标、尺寸和纹理名称，可按原矩形取图；其中仅替换已经完成、属于该花色的卡牌槽位，其余保持原图。

原客户端同一资源只对应一个底图槽位，例如不同花色的 `Shan_png` 共用原图集的一个矩形。把一张新的 `cards.png` 原位替换后，该资源的所有牌只能显示同一款装饰花色。**原位合并兼容坐标，不等于已经兼容按真实花色选图。** 四页素材需要后续客户端适配按资源和显示花色选择页面；本长任务只交付素材及映射，不宣称自动接入。

底图不绘制左上点数和功能花色，继续为原生独立 UI 图层留位。右下的武器范围、火/冰/雷及“国”徽记属于本批静态底图内容；其设计取值不修改官方牌数据。

2026-10-21补充的最终交付门槛：须同时包含[通用图层](../通用图层/README.md)中4花色与13点数共17个38×34透明PNG、独立`ui-layers/manifest.json`、逐项来源/生成ID/SHA及布局映射。点数四花色共用，UI尺寸19×17；点数位置物理(8,8)/UI(4,4)，花色物理(8,38)/UI(4,19)。17项与197项底图分别计数，完整交付前两份检查点均须全部验收，52种点数花色组合的可见Alpha应互不挤压。

完整包复制`ui-layers/38x34/`、可移植来源记录与布局清单，离线预览可选择点数/花色并准确叠加；不得只交卡面atlas或把点数烘焙进底图。`build_delivery.py`现已接入17图层输入门槛、52组合校验、文件冻结和复制回读，主交付须197卡面与17图层均通过才可创建。此处仍不提前生成完整atlas、不宣称已接入游戏。

## 输入与冻结口径

| 输入 | 用途 |
|---|---|
| [scope.json](scope.json) | 用户保留名单、名称、布局、范围覆盖、生成约束 |
| [tasks.json](tasks.json) | 精确资源花色任务、代表牌、牌号证据、复用关系与范围差异 |
| [inventory.json](inventory.json) / [inventory.md](inventory.md) | 原图资源全集与每项处理决策 |
| [原始拆分 manifest](../../卡牌拆分/manifest.json) | 原矩形、scale、sourceSize、spriteSourceSize、共享别名、原始哈希 |
| [原始图集](../../卡牌拆分/source/cards.png) / [原始 atlas](../../卡牌拆分/source/cards.atlas) | 每一页合并的不可变底图与 atlas 字节 |
| [现有合并工具](../../../tools/card_atlas.py) | 经核验的 split / compose / merge / verify 行为；仓库路径为 `tools/card_atlas.py` |
| [原生 UI 与合并依据](../../../doc/sanguosha.md) | 三层布局、原位合并和已知接入边界 |
| [通用图层清单](../通用图层/manifest.json) / [独立检查点](../通用图层/state.json) | 4花色与13共用点数的17项验收、布局和成品SHA；不计入197项底图 |
| [通用图层验证](../通用图层/validate.py) / [验证报告](../通用图层/verification.json) | 完整交付须运行`validate.py --complete`，验证17项、52组合、复用字节与真实Alpha |

盘点快照：111 个 atlas 条目、109 个独立矩形；87 个资源需要制作，24 个资源沿用原图，其中 20 个由用户明确排除、4 个没有可用卡牌信息。197 个资源花色映射对应 194 份唯一视觉，另 3 项为同色共享矩形复用。普通花色编码为 `1=heart`、`2=diamond`、`3=spade`、`4=club`。

| 页 | 有效资源花色映射数 | 实际替换矩形数 / 唯一视觉数 |
|---|---:|---:|
| heart / 红桃 | 40 | 40 |
| diamond / 方块 | 51 | 51 |
| spade / 黑桃 | 56 | 55 |
| club / 梅花 | 50 | 48 |
| 合计 | 197 | 194 |

这是当前盘点的验收预期，执行时必须由冻结输入重算并比对。新证据改变范围时，先更新主配置与队列，再重建交付；不能在合并器里静默补色或遗漏任务。

单张体积按用户最新要求控制：186×260生产PNG须≤200,000字节，`check_task`在完整合并前核验；工作区默认浏览使用每张同样≤200 KB的压缩WebP副本。该上限针对单卡常用文件，不把744×1040有损查看副本当作图集输入，也不强行把整张2048×4096 atlas或原始溯源PNG压成200 KB而破坏像素校验。

随后用户要求省token并反馈186×260放大模糊：高清WebP现为实际查看交付文件，不再额外生成预览或中间底图；186×260仅保留作原图集兼容。最终包还需收录每项高清WebP及来源/尺寸/SHA映射（建议`cards-hd/<resourceKey>/<suit>.webp`），由同一次原生生成直接导出，不增加生成次数。当前工作区已自动产出高清文件；`build_delivery.py`尚未增加高清文件复制映射，主流程应在全部卡面完成后的最终交付步骤补齐并回读验证，不将现有186×260+UI打包逻辑描述成已覆盖高清交付。

生产底图统一沿用目标矩形的物理像素大小。本次生成项为 186×260，原 `DJJ_Zhao_png.png` 为 200×282 且保留原图，不能为了整齐把它改成 186×260。高清生成原图、历史样板、提示词、原始图集和调查资料留在原档案中；交付以复制或新写文件完成，不迁走或覆盖它们。若完整交付需要可移植归档，`provenance/` 必须复制内容，不能留下指向机器绝对路径的链接。

197 个逻辑 PNG 包含 3 个复用副本。复用副本必须与其源文件 RGBA 一致，并在映射中写明 `reuseOfTaskId`；不调用生成工具再画一遍。归档交付优先普通文件复制，不依赖跨设备硬链接或符号链接。

通用图层采用固定ID：`suit_heart/suit_diamond/suit_spade/suit_club`和`rank_A/rank_2`至`rank_10/rank_J/rank_Q/rank_K`。红桃与点数2的成品保留既有38×34 PNG原字节；另存的历史高清来源只供风格参考与溯源，不替换已确认成品。重新导出候选须保留原生成ID与原图SHA，并明确`derivation.newGeneration=false`，不能将导出修订计为新生成。

图层门槛调用`validate.verify(exercise_writes=False)`执行纯只读检查，不创建临时写入测试或改写原验证报告；单独的`validate.py --complete`默认仍执行不可覆盖写入测试。包内组合预览的示例底图路径改为`../cards/WuZhongShengYou_png/heart.png`，返回链接仍指向包根预览，不能留下依赖原工作区`生产底图`目录的运行路径。源记录的绝对路径只作历史溯源；实际消费采用相对路径清单。

## 精确 variant map

`variant-map.json` 建议记录 `schemaVersion`、`buildId`、输入哈希、原始页、花色页、资源表与验证计数。不得仅建立“红桃 -> 红桃页”的全局映射。资源键和花色必须共同参与查询。

资源表为原 111 项各列出四个普通花色，共 444 个明确决策：197 项 `generated/reuse`，247 项 `original`。后者包含用户保留资源的 96 项和待制资源中不存在的 151 个花色组合；这些是回退映射，不是补生成任务。花色为 0、未知花色、未知资源均另行记录回退策略，不伪造黑桃或其他默认花色。

每个普通花色记录至少包含：

| 字段 | 要求 |
|---|---|
| `resourceKey`, `suitValue`, `suit` | 精确逻辑键；普通花色沿用 1～4 编码 |
| `decision`, `reason` | `generated`、`reuse` 或 `original`；写清保留、缺色或复用原因 |
| `taskId`, `reuseOfTaskId` | 生成/复用追溯；原图项为空 |
| `pageImage`, `pageAtlas`, `frameName` | 具体相对文件与原 atlas 条目名；回退必须指向 `original/` |
| `frame`, `scale`, `sourceSize`, `spriteSourceSize` | 原样保存 manifest 字段，不仅复制 x/y/w/h |
| `standalonePng`, `rgbaSha256`, `fileSha256` | 独立 PNG 与校验；原图可指向原始裁切来源 |
| `sharedFrameGroupId`, `sharedFrameNames` | 所在物理槽和全部资源别名 |
| `sourceCardIds`, `representativeCardId` | 实际花色证据与代表配置，不能把代表牌号当唯一实体牌 |
| `displayName`, `badge`, `weaponRangeVariants` | 静态文字及已知模式差异；赤血刃按用户指定 3 标记覆盖 |
| `integrationStatus` | 固定为素材已交付/客户端未接入，直到另有真实接入验收 |

查询顺序：先查资源是否存在、是否属于原图保留项，再查该资源的实际花色白名单，最后验证目标任务已完成及文件可读；任何一步不满足均选原图。最终完整交付不允许把应生成却失败的任务悄悄记作“正常原图保留”；未完成时只能发布明确标记的阶段预览和缺项报告。

`card-id-map.json` 是已冻结配置的来源索引。它不能替代运行时当前点数、当前显示花色或技能的仅 UI 覆盖参数。底图和左上小花色未来需遵循同一次原生显示口径：普通 `DisplayFlower`/`UpdateCardFace` 与直接 `ChangeFlowerAndNumber` 两种入口分别取正确数据，避免卡面大花色和小花色相互矛盾。

## 共享矩形的特殊处理

| 共享组 | 原矩形 | 同花色规则 |
|---|---|---|
| `TengJia_png` / `TengJia2_png` | `(198,2148,186,260)` | 黑桃、梅花均复用同一视觉，2 份视觉映射为 4 项 |
| `ShuiYanQiJun_png` / `ShuiYanQiJun2_png` | `(392,1880,186,260)` | 梅花复用；黑桃仅 `ShuiYanQiJun2_png` 有实体证据 |

每页按 `(x,y,w,h)` 分组，只写一次；同页同组出现不同生成像素必须报错并保留检查点，禁止以后遍历者覆盖前者。原工具 `compose()` 已有共享修改冲突检查，应继续使用。

水淹七军的黑桃是不能省略的边界：黑桃页共享槽写入 `ShuiYanQiJun2` 后，物理上 `ShuiYanQiJun` 别名也会读取到黑桃图。**这不产生一项新的合法生成映射。** `ShuiYanQiJun_png + spade` 仍必须明确指向原始页；不能因为该名字存在于黑桃 atlas 就当作已支持黑桃。报告把该物理传播列为 `shared-slot-incidental`，不计入 197 项，更不改实际花色白名单。

这一例也说明四页 atlas 不能单独承担全部选择规则；使用者必须读取 variant map。若未来要求每页同名条目对缺色别名仍物理保持原图，则必须拆共享槽、重排 atlas，已超出“保持原 atlas 原位合并”的交付模式。

## 可执行合并步骤

正式入口现已实现为 [build_delivery.py](build_delivery.py)。它复用原工具的 atlas 矩形校验，以同样的“原图副本 + 无 mask RGBA 覆盖”语义直接合成四页；不用先落盘四套完整拆分 staging。下面的 `split/verify/merge` 是可手工复核的底层方法。自动入口在每页写入后重新打开 PNG，逐槽及逐通道验证间隙与透明 RGB。

1. **冻结与验收输入。** 保存 scope、tasks、inventory、manifest 和生成记录的哈希；验证源 PNG/atlas 哈希、全部生成项完成、197 项映射齐全、194 份视觉可读、3 项复用成立。记录点数/左上功能花色未烘焙的人工检查结果。当前配置的原始文件 SHA-256 分别为 PNG `14e786fd774fc5a9e1de952ad6a042ec5b87220bf434bc2d8410584eae01c3df`、atlas `f4ee16929bce2f4beb04020f87f8e4bdc267942a166bcda63913ace3d3630f15`；现场仍需重算。
2. **建立新 staging。** 每个花色一个新工作目录，含 `source/cards.png`、`source/cards.atlas`、完整 `cards/` 和 `manifest.json`。可直接用现有工具 `split` 从原图建立，不能在历史 `卡牌拆分/cards/` 上批量覆盖，也不能复用上次未验收的 staging。
3. **原图基线检查。** 在尚未写入新素材时执行 `verify`，要求 111 项未编辑合回原图后 RGBA 逐字节一致。现有 `verify` 只适合此基线；替换后应当不同，不能把它用作成品验证而误判失败。
4. **按花色与共享组写入。** 只收集当前页实际任务；读取已通过检查的生产 PNG，验证物理尺寸、RGBA。共享组核对像素哈希后一组写一次；在 staging 中将该像素复制到共享组的全部别名文件，使原工具看到一致的共享修改。缺色组、用户保留组、无信息组保持原始裁切。水淹七军黑桃例外的逻辑回退由映射处理，不能据 staging 别名文件数推断任务数。
5. **原位合并。** 逐页运行现有 `merge --workspace <staging花色目录> --output <新输出花色目录>`。工具从原图构造输出，并以无 mask 的 RGBA 替换写入槽位，保持 atlas 原字节；不自动缩放、不重排、不将图集分配成不同尺寸。
6. **构造清单与验证。** 生成精确 variant map、实体 ID 索引、共享传播记录、逐图哈希和完成计数；按照下一节验证回读的实际 PNG，不能仅采信内存对象或 CLI 返回码。
7. **发布本地交付。** 完整产物先写入新批次临时目录；验证通过后原子改名为正式 `<批次ID>`。将完成路径、哈希与报告写入主任务检查点，再更新预览入口。失败保留 staging 与错误记录；恢复只重跑受影响页，不重画已经完成的单卡。

现有命令示例，均在仓库根目录运行，目录名为占位值，实际须使用本批全新的目录：

```powershell
& '.\.venv-card-atlas\Scripts\python.exe' -X utf8 tools/card_atlas.py split --atlas '卡牌归档/卡牌拆分/source/cards.atlas' --image '卡牌归档/卡牌拆分/source/cards.png' --out '卡牌归档/塔罗牌卡面/长任务/runtime/staging-批次ID/spade'
& '.\.venv-card-atlas\Scripts\python.exe' -X utf8 tools/card_atlas.py verify --workspace '卡牌归档/塔罗牌卡面/长任务/runtime/staging-批次ID/spade'
# 在上述工作目录中写入本页已验收底图、协调共享别名后，再执行 merge。
& '.\.venv-card-atlas\Scripts\python.exe' -X utf8 tools/card_atlas.py merge --workspace '卡牌归档/塔罗牌卡面/长任务/runtime/staging-批次ID/spade' --output '卡牌归档/塔罗牌卡面/交付/批次ID临时/atlas/spade'
```

`split/verify/merge` 与自动入口均已存在。若现有虚拟环境不可用，先确认 Pillow 依赖再运行，不改游戏依赖或发布映射。

## 单张替换和客户端边界

如需一张保持原文件名的代表版 `cards.png`，可额外建立 `representative/`：按共享矩形挑选一个已完成代表任务，优先有军争代表的任务，再按代表 ID、花色编码和任务 ID 稳定排序；该矩形的所有别名使用同一图。清单记录每个槽位究竟选择哪个花色，原图保留项始终保留。

代表版具有几何和文件格式兼容性，但只适合固定代表花色的离线展示或受限替换。一个多花色资源的其他牌仍会显示该槽位的代表装饰花色；即使只出现一种实际花色，也还存在技能改色和隐藏符号等场景。不得将其命名或宣传为“全花色完美替换版”，也不默认安装到游戏。

四页 atlas 的 `meta.prefix` 均保持原 `cards/`。若未来把四页直接交给原加载器并同时注册相同逻辑纹理键，可能相互覆盖缓存。适配方需要用页面句柄加原矩形创建纹理，或用明确页面命名空间隔离缓存，再经 variant map 取对应纹理；不能全局轮流覆盖 `cards/<name>.png` 来表达每张牌的花色。

武器范围为静态代表配置。寒冰剑、贯石斧、青釭剑、丈八蛇矛存在特殊模式范围差异；任务保留的 `rangeMismatchCardIds/weaponRangeVariants` 必须继续进入交付清单。四花色页面不能自动消除这类“同资源同花色、不同模式范围”的差异；若未来要求逐模式完全正确，需进一步拆分范围徽记图层或扩充变体键，属于另外的接入工作。赤血刃范围 3 是用户明确的美术覆盖，必须保留这个来源说明。
