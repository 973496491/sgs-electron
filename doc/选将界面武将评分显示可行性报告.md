调查日期：2026-11-19。按用户要求，仅核查和写报告，没有修改功能代码、注入游戏或同步运行环境。

## 结论

2026-11-20最新现场结果：日志证明评分565行及候选读取正常，全部0是本功能门面GameContext不可达、维度为0。已修复独立引擎出口，并在原生全局出口均不可用时从有明确模式证据的选将窗口读取身份。30组验证覆盖修前复现、军八四身份、地主/农民与换将；主公15/1/475恢复4/3/10，740缺分仍0。当前待用户重载后游戏内复测，详见架构表“全0现场定位与上下文访问修复”。

2026-11-20现场追加：用户验证军八/斗地主均显示0/10，已补“配置加载阶段+源/模式/候选九维”诊断及打开调试时即时快照，未修改评分和回退规则。当前仍缺现场日志，不能将整包解析故障注入结果当成真实原因。操作和23组验证见架构表“军八/斗地主全0诊断”。

**可以实现“在本人选将卡下方显示当前场景对应的系统强度评分”。界面对象、武将ID、模式/身份信息和评分数据结构均已找到。**

但这还不是已经接通、可以直接启用的功能：当前小抄没有现成的评分读取适配接口；原生评分管理器位于主程序闭包内，本次未在运行中的游戏取得该实例。后续需要补齐数据访问适配，并针对不同选将窗口安排文字空间。不能承诺每个武将、每种玩法都必然有分，也不能把旧快照表内嵌后称为“当前系统实时判定”。

可行范围是展示客户端当前已知的系统评分，不是重新计算武将强度。对没有对应分数的卡，显示“暂无评分”或隐藏；对身份/先后手尚未确定的场景，应说明未确定，不能用最高分替代。

## 1. 显示什么分数

沿用上一份 [武将评分逻辑调查](武将评分逻辑调查.md) 定位的 `WuJiangs.CharGrade`，以武将实际ID读取原生评分模型，按照当前玩法选择对应维度。这里的“系统评分”指这套模式强度分，不是本局预测胜率、推荐标记或玩家武将战力。

| 当前场景 | 应显示的评分 | 显示例子 |
|---|---|---|
| 普通身份，主公已确定 | `grade3 / Grade_3` | `主公评分 8/10` |
| 普通身份，忠臣已确定 | `grade4 / Grade_4` | `忠臣评分 7/10` |
| 普通身份，反贼已确定 | `grade5 / Grade_5` | `反贼评分 9/10` |
| 普通身份，内奸已确定 | `grade6 / Grade_6` | `内奸评分 9/10` |
| 斗地主，地主 | `grade8 / Grade_8` | `地主评分 9/10` |
| 斗地主，农民 | `grade9 / Grade_9` | `农民评分 9/10` |
| 与评分表相匹配的排位/欢乐，先后手已确定 | `grade1 / grade2` | `先手评分 9/10` |
| 对应国战玩法 | `grade7 / Grade_7` | `国战评分 6/10` |
| 身份/先后手未确定 | 暂不取单一分数，或明确并列维度 | `先手9 / 后手8`，或`身份未定` |
| 表中没有对应玩法或分数 | 不估分 | `暂无评分` |

例如，本地配置中吕玲绮716的忠臣分为7、反贼分为9：同一张武将卡，在忠臣和反贼身份下应显示不同数字。不能简单取它的最高分9显示在所有模式。

需要注意：

- `SelfFigure` 数值在不同玩法复用。原生 `Lm` 中主公和地主均为1，反贼和农民均为3；必须先判断玩法，再解释身份，不能仅按数字取分。
- `GameContext.FirstHand` 确实存在，以有效座位的 `FixedViewId` 和 `IsLegalOperable` 判断本人先后手。但它初始假定为true，座位未就绪时不能仅凭返回true就确认先手；还需校验相关座位和场景状态。
- 不应从 `fe.getGradeList()` 的结果中找当前身份分数：这个方法会筛选模式并最多保留5项，当前需要的维度可能已被丢弃。应读取原始九项评分，再沿原生 `Math.ceil` 规则显示整数。
- `GetHighScoreByTab` 是取某类模式的最高项，`MaxGradeIndex` 是找最高维度，都不能替代当前身份对应项。
- 0、缺项、无对应玩法不能自动补为平均值、同名武将分数或默认分。

## 2. 已确认的选将界面入口

不是只有一个选将窗口或一种卡片实现，不能仅挂旧版窗口就承诺全覆盖。

| 原生窗口 | 本快照类 | 已确认的候选卡链 |
|---|---|---|
| `SelectGeneralWindow` | `qCs` | `ShowGenerals -> new l4i -> item.Card -> generalUis` |
| `SelectGeneralDdz2023Win` | `lLs extends qCs` | 复用普通候选卡链，另有亮将及选定后的飞入动画 |
| `SelectGeneralHappyWindow` | `RLs extends qCs` | 有本人 `generalUis` 和队友 `teamMateGeneralItems` 两套列表 |
| `SelectNewPaiWeiGeneralWindow` | `XLs extends RLs` | `initGeneralUIs -> new rSs`；继承链为 `rSs -> fes -> l4i -> Rii` |
| `SelectGeneralHappyNewWindow` | `rLs extends qCs` | `initGeneralUIs -> new Cai`；继承链为 `Cai -> fvt`，与l4i不是同一条卡片链 |
| `SelectCountryWarGeneralWindow` | `QCs extends mIs` | `createCardUI -> new yci`，另有主/副将拖动与槽位 |

原生 `getCurrentSelectGeneralName` 按当前玩法路由实际窗口，普通场默认 `SelectGeneralWindow`，部分排位/训练分支走 `SelectNewPaiWeiGeneralWindow`，斗地主2023等走 `SelectGeneralDdz2023Win`。`SelectGeneralHappyNewWindow` 虽有注册和完整实现，本次所查路由没有直接选它的分支，因此应作为兼容候选，不能只因名称有“New”就当成当前排位的唯一入口。

每个候选对象可通过 `Card.CardId / CardID` 取得实际ID。普通和小卡两条链的 `set Card` 都会调用 `UpdateCardFace`；原生换将 `RespChangeGeneral` 会给已有卡对象重新赋 `Card`，新版SP替换也可能在原对象上换ID。因此显示不能只在第一次开窗建立，还必须随实际ID变化刷新。

建议第一阶段只在本人候选列表中显示。主公展示卡、队友选将页、锁定占位和对方展示卡必须区分；如果以后也显示队友卡，应按队友的场景/身份计算维度，不能照搬本人的先后手或身份。

## 3. 武将卡下面能否放得下

**能增加文字节点，但原窗口没有统一预留的“评分行”，必须一起适配布局。**

原生普通武将卡基准为94×131，小卡基准为61×61；`SetScale` 还会改变卡片实际尺寸。评分应跟随当前卡片的实际底边定位，不应把94、131直接写成所有窗口的固定坐标。

已发现的空间限制：

- 普通窗口双排布局中，两排卡之间仅额外间隔7像素；新排位 `XLs.resetGeneralCardUiPos` 的纵向间隔为15像素。增加一行约14～18像素的字，不能在原布局中一律保证无重叠，选中边框和SP标记还会占用边缘空间。
- 普通卡已有推荐、胜率、皮肤标记、换将按钮和SP展开UI。`ShowWinRate` 在不同模式还会切换到卡内、上方或卡下方的位置，不能把它的背景/文本直接改成评分，也不能覆盖 `hideWinRate` 改动胜率语义。
- 原窗口包含倒计时、换将卡数量、确认按钮及选定后的动画。调整卡行距时应核对这些控件的空间；国战还要单独检查拖动与主副将槽位。

建议显示为独立的一行，例如 `忠臣评分 7/10`，居中放在本人候选卡的下面。标签应不接收鼠标事件，不改变原卡片的点击、悬浮、拖动或选将判定。常见做法是让标签跟随卡对象，或由所属窗口在独立显示层同步位置；具体选法须在实现时核对该窗口的裁切和动画，源码核查不能证明所有分辨率下都已放得下。

## 4. “当前系统评分”的数据访问还差什么

已确认的原生读取接口是 `aMt.GetGeneralCharGrade / GetGeneralCharGradeByID`。它按当前客户端已载入的配置和评分缓存返回 `fe` 模型，不发送选将操作，也不会因为读取就自动查询服务器。

但 `aMt` 是该快照的闭包内类名，不是可直接在小抄中使用的全局对象。本次检查的原生注册/导出没有发现把它直接暴露出来；现有小抄 `laya.class` 的管理器映射也没有评分配置管理器入口。已有的 `GameGeneralManager` 对应的是原生 `nhi`，不能把它误当成 `aMt`，更不能凭空调用 `laya.class("CardManager")` 并认定能工作。

后续实现必须先提供一个实际可达的数据适配接口，取得当前客户端的评分模型或当前版本配置，并核对原生缓存补缺规则。这个接口应对外返回“有效分数 / 当前维度缺项 / 场景未定 / 数据源不可用”等明确结果；具体如何获得运行期评分对象，仍需实施时验证，**本报告没有把它记为已经接通**。

若仅使用目前保存的565项离线表，可以做一个有版本范围的静态评分展示，但不满足严格的“与当前运行客户端评分一致”。新武将缺项时也不能强行查同名版本。106016/106017评分协议虽然有实现，本次没有证明当前选将会主动查询它；不应把补发网络请求作为本报告已验证可用的前提。

## 5. 如果实施，模块和验收边界

以下是建议方案，不表示已完成开发。

- **评分适配**：负责当前评分源、玩法、身份、先后手及原始评分项读取；不改写原生评分模型，不发送选将操作。先通过这一层确认当前运行数据可读，再接显示。
- **选将评分显示**：负责当前窗口中的本人候选集合和文字节点；每个卡对象对应一份显示状态，包含当前武将ID和显示维度。安装应幂等，换将/替换ID/页面切换/缩放后刷新，关窗与节点销毁时清理。
- **公共挂钩协调**：保留原生 `Card` 更新、布局、推荐、胜率、SP、皮肤、点击与动画语义。不得只在首次初始化挂一次后假设所有后续卡和窗口都复用；卸载不能覆盖其他功能后来安装的包装器。

主要验收行为：

1. 身份场、斗地主及匹配的排位场景，卡下分数与同ID、同维度的原生评分一致；维度未定时不误标。
2. 换将、SP切换、快速切页后，分数跟随实际卡ID变化，不残留上一个武将的数字。
3. 缺分武将、无匹配玩法和数据源不可用有明确表现，不显示伪造的0分或最高分。
4. 单排、双排、缩放、SP展开、推荐/胜率共存时文字无覆盖；点击、换将、倒计时和选定动画保持正常。
5. 重开窗口不叠加文字或监听，关闭窗口和换局后没有残留，旧异步结果不会写入新窗口。
