# OL 武将评分逻辑调查

调查日期：2026-11-19。范围：本地已有的 OL 普通 ES6 主程序和普通配置，仅调查，没有修改小抄或游戏运行环境。

> 2026-11-20后续：已按用户授权接入选将评分验证版，从现有官方配置加载结果`XC.initMap.generalGrades`取当前模式/身份分，卡下显示`N/10`，缺分为`0/10`，无UI开关。详细职责、验证及同步见[架构表](代码架构表.md)“选将评分验证版”。本文保留最初调查证据，基础评分制定公式仍未找到。

## 结论

**能找到武将“强度评分”的现成数据，以及客户端读取、补充、缓存和展示逻辑；没有在这条链上找到基础分数的制定或生成公式。**

本地 `character.json` 不只有武将姓名、技能、势力等基础信息，还包含 `WuJiangs.CharGrade`：565 个不同武将 ID 的评分记录，已有数值均为 0～10 的整数。评分按模式、身份分别保存，并非每个武将一个统一总分。

客户端优先使用配置中的分数，缓存和服务端回包只能为缺少记录的 ID 补充数据。由此能确认“端上有评分表和消费逻辑”，不能确定这些分数原先由人工配置、胜率统计还是其他服务端算法产生。本次到此收束，没有继续追查服务端或做全客户端解包。

配置位置为 `tmp/ol-lamp/character.json`，共1651条武将记录；其中包含多种模式、版本或特殊角色，不等于1651个普通可选武将。

## 3. 已核实的读取与显示逻辑

### 数据来源优先级

`aMt.initGeneralCharGrades` 先把 `configData.WuJiangs.CharGrade` 转成 `fe` 评分模型，再读 `Cg.GetAllSaveGeneralGrades()`。缓存只有在相同ID尚不存在时才加入，因此配置优先。

`SetGeneralCharGrade / SetGeneralsCharGrade` 处理外部评分数据时，也会跳过已经存在的ID；不是收到回包就覆盖配置或合并单个维度。有效新记录写入内存和 `GENERAL_GRADE_SAVE_DATA`。`NeedUpdateGeneralGrade` 根据 `LocalServerTime` 判断是否换日，换日清持久缓存并通知读取方重建内存表，静态配置仍会重新载入。

**仅调用 `GetGeneralCharGrade` 不会自动发送评分请求**：这个方法初始化本地表后，直接把当前缓存结果交给回调。

### 界面入口

武将详情的 `showPingding -> Izt.ShowPingdingInfo -> GetGeneralCharGrade -> Czt` 读取评分并创建雷达图；商城等位置也有 `new Czt` 的消费入口。`Czt.showTipHandler -> k_i.updateData` 将模式名与 `CHR_INFO_EXPERT_SCORE="强度评分"` 组合为提示标题，说明来自 `CharTips`。

已读到的展示规则：

- `fe.onUpCharGradeData` 跳过缺值及非正数，使用 `Math.ceil` 向上取整；按原始值 `<=4 / <=7 / >7` 生成三档状态。
- `fe.sortCharGradeData` 结合 `CanUseGeneralInMode` 整理候选，排位不可用项会被剔除，其他不可用模式项可移至后部，再择取较高分项，最多保留5项；同分和最终顺序受原候选顺序影响，并非九项完整展示或简单全局降序。
- 详情面板有效项超过3个才显示评分图，否则使用无数据表现。
- 雷达图顶点按 `grade / 10` 缩放，说明显示尺度为10分；这属于绘图比例，不是基础强度计算公式。
- 模型还保留 `GradeSwitch1/2` 的显示条件，本地565条评分记录均未提供这两个字段，初始化后默认为0。

评分表由原生数据管理器维护，显示模型的候选列表由 `fe` 按需建立并缓存；图形、动画及提示属于 `Czt/k_i`。原生图形 `destroy` 清理定时器、图形与引用。本次没有新增状态、挂钩、初始化入口或清理责任。

## 4. 评分协议：发现定义和消费实现，未实发

| 协议ID | 名称 | 本次核实范围 |
|---|---|---|
| 106016 | `encodeClientGeneralScoreBatchDataReq` | 批量请求，字段 `generalId` 为ID列表 |
| 106017 | `decodeClientGeneralScoreBatchDataResp` | 返回 `generalData` 列表；管理器响应处理调用 `SetGeneralsCharGrade` |
| 170023 | `encodeClientGeneralScoreDataReq` | 单个ID请求的注册与编码定义 |
| 170024 | `decodeClientGeneralScoreDataRep` | 单条 `generalData` 的注册与解码定义 |

`Bnt` 解码出的每条记录包含武将ID与上表九个分数字段。`SetGeneralsCharGrade` 将回包字段分别除以10后放入评分模型；例如假设收到 `zhugong=71`，模型为7.1，展示取整后为8。**71是验证缩放规则的合成值，不是任何真实武将的实测回包。** 配置中的 `Grade_3=8` 则直接载入，不会再除以10。

批量管理器 `ClientGeneralScoreBatchDataReq` 确实有发送、5秒超时和回调清理实现，106017也有事件订阅及响应处理；但本次主程序中该请求方法名只出现于方法定义，没有找到详情界面直接调用它的链路。170023/170024同样不能仅凭注册证明当前在线使用。因而不能保证“静态表缺项时，打开详情就会自动补齐评分”。

## 5. 容易混淆的其他分数

还发现 `RANK_NEW_TYPE_GENERAL_SCORE_*` 排名常量，对应榜单文案为“武将战力”；这和详情中的模式强度评分是不同数据用途。本次没有扩大到战力成长或排行榜计分规则。

另有 `TechScore / GetTechScoreById` 的五项数组兼容代码，缺失时返回 `[40,40,40,40,40]`。但本地1651条基础武将记录没有任何 `TechScore` 字段，`GetTechScoreById` 也没有找到直接调用点，不能把这个默认数组当成当前武将真实评分。

本次没有发现从技能效果、胜率、品质、价格等在端上实时推导 `CharGrade` 基础分数的公式。能确认的是评分已经作为数据存在于配置或协议中；不能据此断言服务端一定按某种算法计算，或评分由玩家投票产生。
