# 十周年皮肤迁移到 OL 本地链路可行性报告

> 第1～8节保留最初只读调查的结论和边界。用户随后授权修改并同步，指定用于 OL 吕玲绮；已实施状态及验证步骤见第9节。

调查日期：2026-11-18。范围：评估十周年素材能否接到本机现有 OL 小抄“本地皮肤”链路。本次只读代码、解析已有数据、取得少量公开素材样本并编写报告；没有修改源码、安装文件、发布配置或 asar，没有热注入、重启或执行游戏操作。

## 1. 结论

**可以把十周年的画面素材接到 OL 的本地显示链路，但当前功能不支持直接导入十周年皮肤包。静态图片替换最有把握；动态展示有可利用的格式基础；完整复刻十周年皮肤的所有效果还需要专门适配。**

这里的“搬到 OL”应当定义为本机使用十周年素材显示某个 OL 武将，而不是把十周年皮肤变成服务端认可的 OL 皮肤。两边武将、皮肤编号、配置和效果系统不能视为同一套。

| 目标 | 可行性判断 | 现有链路能否直接完成 | 主要条件 |
|---|---|---|---|
| 用十周年立绘替换一款 OL 皮肤的静态显示 | 高，属于资源与布局适配问题 | 不能直接导入，需增加资源映射 | 对齐大图、座位图、缩略图及裁切 |
| 十周年背景与角色待机动画在 OL 播放 | 有依据，值得做单皮肤验证 | 不能直接完成 | 优先检查十周年 `.sk` 与 OL 旧骨骼分支，适配分层、缩放、动作 |
| 直接把十周年 Spine JSON 地址交给 OL 新版动态链 | 不能认定兼容，样本有明确差异 | 不可直接套用 | 样本 Spine 3.6.38，OL 相关加载分支选择 4.0，动作名也不同 |
| 出场、攻击、技能、全屏特效、语音完整复刻 | 有条件，工作范围大 | 不能直接完成 | 每款资源及事件语义分别核查、映射和验收 |
| 在原生皮肤选择器中新增独立十周年条目 | 技术上可设计，但比替换素材复杂 | 当前没有该导入能力 | 本地目录、映射、数据对象、列表筛选、详情依赖及发送隔离 |
| 让其他玩家看到本机导入的十周年皮肤 | 当前本地方案不能实现 | 不能 | 服务端与其他客户端没有这份本机映射及资源 |

**如果要求以后也完全不修改任何代码，只复制十周年文件进去就能在现有按钮下使用，目前没有证据表明本机支持这种操作。** 本次“不要改代码”的要求已遵守；下文的改动项仅为评估方案。

## 2. 当前 OL“本地皮肤”实际做了什么

### 2.1 现有入口和链路

工作脚本 `electron-next/resources/daxiaochao.user.js` 与实际安装脚本 `%APPDATA%/SGSOL/三国杀打小抄.js` 本次读取时 SHA-256 相同。

当前主要链路为：

```text
点击“本地皮肤”
  -> runLocalSkinEnableInline()
  -> 发现原生换肤窗口、选择器和皮肤条目
  -> hookItem / applyHasSkin
  -> 让已有 OL 条目可选，并按条件补动态状态
  -> closeSelectSure 记录本地选择
  -> localSkinSelections.send 在发送时临时换回真实默认值
  -> localSkinSelections.apply 在匹配身份的响应列表里应用本地选择
  -> 原生 OL 皮肤对象生成资源地址并渲染
```

关键点：**现有逻辑主要改变 OL 条目的本地选择及显示状态，并不自动把外部图片或骨骼文件转换成新的 OL 皮肤对象。**

### 2.2 OL 仍然要求存在自己的皮肤数据

11月18日保存的 OL 主程序中：

- `GetGeneralSkinBySkinID(t)` 从 `SkinIDDict` 查找配置对象。
- `GetGeneralSkin(t,...)` 从 `GeneralSkinDict` 取得武将对应列表，再进行展示、合成时间等筛选。
- `SkinBigUrl / SkinMaxUrl / SkinSeatUrl` 使用 OL 皮肤对象及其 `skinID` 生成图像地址。
- 动态部分还读取资源类型、动作配置、多形态配置和专用位置参数。

因此，仅把响应中的 SkinID 换成一个十周年编号，不会自动建立武将对应关系，也不会自动创建骨骼和纹理。编号偶然相同也不能证明是同一皮肤。

### 2.3 发送隔离应继续保留

现有 `localSkinSelections` 保存真实默认 SkinID/动静状态，在调用原生确认方法时临时回传真实默认，随后恢复本地字段。它还按玩家身份、武将、场景代次隔离选择。

未来接外部资源时应沿用这个边界：**服务器继续使用真实 OL 状态，本地显示适配另外处理。** 不应把十周年 ID 或自建本地编号送进 OL 协议，也不应直接修改角色技能、玩法模型。

## 3. 已拿到的十周年证据

### 3.1 本地缓存与配置

前一轮从 Chrome 缓存取得：

- 十周年 `Config.sgs`，包含153个内部文件。
- `GeneralSkinInfoConfig.sgs`、`GeneralSkinSuitConfig.sgs`、`GameGeneralConfig.sgs` 等加密条目。
- 明文 `version.json`，能读取资源路径及版本值。

清单中的静态大图969项、动态资源文件4130项均为文件数，不是皮肤数。已导出的 `skin-resources.tsv` 同时包含 skin 和 general 相关路径，也可能含默认武将图及界面资源，不能当成精确的全部皮肤目录。

目前尚未解出十周年皮肤名称及武将对应表，所以**还不能给出已核实的“十周年皮肤名 → OL武将 → OL承载皮肤”全量映射**。选定少数皮肤时可以先人工核对图像和武将，不必把全量配置解密设为静态试验的前提；若要批量导入和自动分类，这张映射表就很重要。

### 3.2 静态图样本

定向取得官方[543501静态图](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/static/543501.png)：235,062字节，PNG，尺寸 **876×632**。这证明存在可读取的普通图像素材，不等于已适配 OL 座位框。

OL 本地快照中的静态入口包括：

| 用途 | OL 配置对象的入口 |
|---|---|
| 常规大图 | `SkinBigUrl()` → `general/big/static/<skinID>.png` |
| 超大展示图 | `SkinMaxUrl()` → `general/big/bigSkin/<skinID>.png` |
| 座位图 | `SkinSeatUrl`，另有 `staticNew` 和觉醒形态分支 |
| 提示、选肤窗口缩略图 | `SkinUrlInTip / SkinUrlInWindow` 等 |

因此只换一张大图，可能出现“图鉴换了、座位没换”或者切换形态后回到原图。静态素材迁移应按显示用途分别准备裁切、锚点和映射，不能假定一个 PNG 能覆盖所有入口。

### 3.3 动态样本：存在两条格式路线

十周年编号目录 `744001` 的资源清单同时包含 `beijing`、`chuchang`、`daiji` 的 `.json/.atlas/.png/.sk`，另有 `daiji2` 文件。当前未确认这个编号的中文皮肤名或所属武将，也没有证明十周年实际客户端如何组合所有层。

本次取得三个官方 JSON 样本：

| 样本 | 声明版本 | 动作列表 | 说明 |
|---|---|---|---|
| [daiji.json](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/dynamic/744001/daiji.json) | Spine 3.6.38 | `play` | 有骨骼和动画数据，顶层未声明 events |
| [chuchang.json](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/dynamic/744001/chuchang.json) | Spine 3.6.38 | `play` | 不能仅按文件名认定与 OL 出场事件等价 |
| [beijing.json](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/dynamic/744001/beijing.json) | Spine 3.6.38 | `play` | 与角色层分开提供 |

[daiji.atlas](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/dynamic/744001/daiji.atlas) 引用 `daiji.png`，图集声明1682×1682，包含旋转、原始尺寸和偏移信息。迁移应保留匹配的图集与纹理依赖，不能只拿骨骼 JSON。

另一条路线的实物证据是官方 [daiji.sk](https://web.sanguosha.com/10/pc/res/assets/runtime/general/big/dynamic/744001/daiji.sk)：

- 文件内有 `daiji.png` 纹理引用。
- 本次未完整解析其动作表，也未加载绘制，不能以 JSON 的动作表替代 `.sk` 的实测。

**这些结论只覆盖所抽查的文件，不能推广为全部十周年皮肤都采用 Spine 3.6.38，或都提供可用 `.sk`。** 新下载样本与 Chrome 缓存清单也不是同一原子快照，其获取时间和哈希单独保存。

## 4. 动态迁移为什么有希望，为什么不能直接换链接

### 4.1 可以优先研究 `.sk` 路线

11月18日 OL 主程序仍有两类播放器：

- Spine 类型 `3/4` 选择 Spine 播放器，相关加载器建立 `Laya.SpineTemplet(Laya.SpineVersion.v4_0)`。
- 其它类型走 `pei` 播放器，其基类继承 `Laya.Skeleton`，经原生动画加载器取得模板。

本机11月16日取得的 OL `laya.ani.min.js` 引擎快照明确声明并判断 `LAYAANIMATION:1.6.0` 和 `1.7.0`。十周年抽样 `.sk` 的版本落在这份快照识别范围内。

由此可以做出的判断是：**十周年素材已有一种可能直接被 OL 旧骨骼解析器接受的交付格式，值得优先验证，未必需要先把 Spine 3.6 全部转换为4.0。**

但这只是格式层面的可行依据。尚未验证当前实际运行引擎是否与这份快照相同，也未验证该 `.sk` 的纹理加载、混合效果、骨骼变换和最终画面。不能写成“已能在 OL 播放”。

### 4.2 Spine JSON 路线需要额外验证或适配

抽样十周年 JSON 声明3.6.38，当前 OL 相关路径选择4.0。不能通过改文件后缀、把 `skeleton.spine` 字段改成4.0、或把 `restype` 直接改成3，就认为完成格式转换。

如果以后走这条路线，需要验证匹配运行时、可用导出/转换流程，或设计隔离播放器。当前没有证据说明现有 OL 新版播放器能直接正确解析这些3.6样本；也没有做过加载失败试验，因此不把它断言为所有路径都绝对不支持。

### 4.3 动作和事件语义还不一致

11月18日 OL 已采用动作配置，而不能只照搬旧文档对 `newSkinJudge` 的历史判断。当前快照的 `ActionConfig / IsNewSkinSystem / HasAction / FormCount` 等会参与播放条件。

原生动作约定包含：

- 待机 `DaiJi`，出场 `ChuChang`。
- 互动 `HuDong`、攻击 `GongJi`、技能 `JiNeng`。
- 角色待机资源 `daiji.json`、前景资源 `qianjing.json`，部分动作使用 `xingxiang` 资源。
- 出框、技能和显示切换等标签，例如 `ChuKuang`、`Skill`、`Ahide`、`Bshow`；不同链路还涉及全屏效果、恢复原立绘及资源清理。

十周年抽样三个 JSON 都只有 `play`，并分在不同文件。就算解析器能读取，也还需要处理“哪个文件在何时播放、循环还是单次、结束后恢复什么”。**把待机的 play 改名为 GongJi 不会生成原本不存在的攻击动画。**

对只有背景/出场/待机素材的皮肤，合理目标是先迁移它实际具有的展示效果，缺少的攻击、技能动作沿用 OL 原有表现或静态显示，而不是承诺完整复刻。

## 5. 接入方案比较

### 方案 A：借用现有 OL 条目，仅替换本地素材（建议首选）

保留一个已有 OL 武将与皮肤条目作为选择入口，在本地建立“这个 OL 条目、当前形态、这个显示用途 → 十周年素材”的映射。

可复用现有按钮、原生选肤、本地选择保存和真实默认回传。第一步只做静态大图、座位图及必要缩略图。这样无需先伪造新的 OL 皮肤 ID，也不必一开始填齐完整商城物品和合成详情数据。

代价与限制：

- 原生入口的名称和编号仍是 OL 条目；如果要独立显示十周年名称或多个来源选择，需要再增加本地界面。
- 不能让用户其他 OL 皮肤因共享资源地址或全局缓存而跟着被替换。
- 需要区分默认形态、觉醒形态、自己与其他座位；映射作用域应明确。
- 素材缺失、关闭映射和切换场景时应恢复原显示；旧的异步加载结果不能覆盖新选择。

**这是复用现有链路最多、最容易得到可验收结果的路线。**

### 方案 B：保留选肤入口，增加十周年动态展示适配

在方案 A 基础上，按单皮肤描述背景层、角色层、前景层、缩放、镜像、偏移、动作及循环规则。优先验证抽样 `.sk` 能否经现有旧骨骼播放器正常显示，再决定是否引入单独的 Spine 运行时。

需要新增的职责是资源描述、动作适配和显示生命周期，而不是把所有规则塞进 `localSkinSelections`。后者继续负责选择和发送隔离。重复打开、换将、换局、后到响应、动画停止、失败恢复和皮肤屏蔽开关都要协调。

如果使用独立展示层，还须保持 OL 头像、血量、技能和点击区域的原生功能，不能仅凭“动画显示出来”判定接入完成。

### 方案 C：建立完整的本地外部皮肤库

为每款素材建立独立本地条目，并提供来源、名称、武将、缩略图、动静资源和动作映射。在展示选择阶段将它映射到 OL 身份，不把外部编号送入原生服务端流程。

相比方案 A/B，还要处理目录装配、列表过滤、数据对象、详情依赖、同名武将与不同版本武将的映射、缓存更新和本地配置迁移。当前原生详情、商城、合成与动作字段均不保证能接受一个只填 ID/名称的对象。

适合未来确实需要多款选择与分类时推进，不建议作为第一款皮肤的验证起点。

## 6. 语音、资源存放和现有环境

十周年清单存在 `voice/skin/.../*.wav` 路径，但技能语音不能仅按双方技能编号一一对应。应按已核对的武将、技能及触发语义建立音频映射，并处理变身、死亡、静音及缺文件回退。当前本地选肤补丁没有因此自动获得跨客户端语音替换能力。

本机 Electron 宿主已有 `myprotocol` 本地文件读取能力，壁纸链路也已有本地素材加载实践，说明本地资源交付有基础。但本次没有证明骨骼相对纹理路径、请求缓存和该协议组合已对十周年素材跑通。不能把壁纸成功直接当作骨骼成功。

如果以后实施，可以选择“在皮肤对象/播放器适配处明确返回本地资源”或“对限定资源请求做映射”。不必先假设必须修改 `interceptor.js` 或重建 asar；应先验证现有接口能否满足。浏览器油猴环境与 Electron 本地协议环境也应分别看待。

现有的“皮肤屏蔽”和宿主特效拦截会影响最终显示，必须作为相邻功能验证。导入素材仍只是本机视觉效果，不会授予账号所有权、收藏收益或服务器侧皮肤效果。

## 7. 建议的验证顺序及通过标准

以下仅为后续实施建议，本次没有执行游戏内验证。

1. **一张静态图。** 确认对应武将，选择一个 OL 承载条目，分别验证大图与座位图；关闭后恢复。首次打开、重开、换将、换局和后到皮肤响应不应导致错图。
2. **一个 `.sk` 待机样本。** 先用与当前运行环境匹配的引擎，在隔离场景加载骨骼和匹配纹理，验证像素、透明、循环及销毁，再接游戏显示层。单次加载成功不等于游戏内适配通过。
3. **背景与出场组合。** 验证层次、定位、缩放、动作结束和恢复；确认旧播放器停止或销毁，不重复加载、不留下遮挡。
4. **按实际素材扩展动作和语音。** 有对应素材才适配，不把十周年文件名直接当成 OL 事件语义。缺少时按明确规则回退。
5. **再考虑目录化。** 多款皮肤时才补全名称、武将映射、独立选择和资源包管理；明确单人、本机范围和服务器真实默认回传。

当前证据还不足以承诺全量导入成功率或工期。最大未确认项是：当前运行引擎对十周年 `.sk` 的实际兼容性、不同皮肤的格式差异、完整的武将/皮肤映射及多形态行为。
