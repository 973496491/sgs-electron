# 原生皮肤跨版本互通链路

2026-11-21补充：本地静态合页的1.0.15通过生成目录的显式家族别名，将卧龙诸葛亮/界卧龙页与谋/标/界/神/武诸葛页放进同一选肤窗口。此扩展只在选肤取数作用域合并来源，不修改本文按原始OL姓名生成的151组/427ID原生互通表或窗口外查询；“卧龙诸葛亮”仍保留完整页名。策略入口scripts/ten-year-skin-family-rules.json、来源pages接口和资源证据见[十周年迁移报告](十周年皮肤迁移到OL本地链路可行性报告.md)第13节；不要为复现此UI行为直接全量改写native-skin-groups。

## 1. 结论

OL 客户端本身就带"同一武将多个版本共用皮肤列表"的机制，字段是 `character` 表里的 `GeneralSkinParent`，由选肤窗口的 `initskinData()` 读取 `GeneralSkinParentIDs` 后合并。官方只给一部分版本配了这个字段（例如 刘备 1 ↔ 界刘备 299），**吴苋 389 与 族吴苋 528 两边都是空值，所以皮肤桶互相看不见**。

客户端侧的打通点在 `GeneralSkinManager.GetGeneralSkinIncludeHide(generalID, ...)`：选肤窗口、在线皮肤列表、皮肤语音列表全部经过它。给它加一层"同组武将合并"，选肤界面即可看到对方版本的皮肤，且不需要改皮肤归属、持有判断或发送字段。

**服务端环节已查清（详见 2.4）**：客户端发送、保存、局内认领三层都不校验皮肤归属，`SaveUsingSkinID` 只看"是否拥有该 skinID"，而跨版本皮肤用的是你本来就拥有的 ID（52801），所以本地写入必然成功。唯一变量是服务端回包是否把 `SkinID` 改写回默认；若被改写，本地皮肤链路（`localSkinSelections` 的"回传默认值 + 覆盖回包"）可完全旁路，代价是本机专属。

### 2.4 选择与保存链（服务端到底管什么）

选肤确认 `closeSelectSure()`（偏移 9749661）：

```js

  this.realGeneralID,   // GeneralID = 当前武将 389
  this.realGeneralID,   // RealGeneralID = 389

```

`realGeneralID` 由 `UpdateInfo(t)` 传入（偏移 9744687），打开谁的选肤窗就是谁，所以跨版本时上报的是 `GeneralID=389, SkinID=52801`，客户端不会把 528 写进 GeneralID。

保存分两条腿，**都不校验归属**：

| 环节 | 实现 | 校验条件 |
|---|---|---|
| 本地写入 | `SaveUsingSkinID(gid, skinID)`（偏移 11167763） | 仅 `GetSkinListBySkinID(skinID)` 非空（全局拥有表）→ 你拥有 52801 即通过；写入 KV `UsedGeneralSkinID` |
| 服务端回写 | `ServerProxy` 收到 `GeneralSkinList` 后（偏移 11170747） | `!Zni.IsInGame && ClientID == Self.ClientId` 时执行 `SaveUsingSkinID(s, h)`，**用回包值覆盖本地** |

局内认领 `IsSkinGeneralId`（偏移 21913367）：

```js
inSkinGeneralId(t, i) { return null != t && null != i && (t == i || !!this.isDefaultGeneralID(t, i)) }
```

`t` 是座位 `GeneralId`（389），`i` 是协议里的 `GeneralID`（也是 389），**第一项 `t == i` 就成立**，无需 `GeneralSkinParent` 参与。

**结论**：客户端三层（发送 / 保存 / 渲染）全部放行跨版本，唯一变量是服务端回包里给的 `SkinID`。服务端若拒绝并回写 `0` 或旧值，本地 `UsedGeneralSkinID` 会被覆盖，表现就是"选完重开回到原皮肤"。

### 2.5 真正的阻塞点：`window.laya` 不是宿主的 `laya`

主脚本 12879 起自定义了一个 `laya` 门面对象，**它不是 Laya 引擎命名空间**。它的 `class(name, force, factory)` 通过内部 `caller` 表解析管理器，表里明确登记了 `GeneralSkinManager: [n(938)]`，同表还有 `GameGeneralManager`、`TaskManager`、`ActivityManager`、`RoomControler` 等四十余项。这套解析按名字从引擎对象上取实例：`manager("GameGeneralManager")` 返回的对象直接带 `LampRewardCanAward`、`atlasGeneralDict`，是真实例而非类。

而 `window.laya` 是引擎命名空间，`class()` 是**注册**语义（`laya.class(name, classDef)`），单参数调用返回空。首版正因为读的是 `window.laya`，名字查找、注册表、图扫描三步全部落在空对象上，`pickHolder()` 恒为 `null`，按钮于是长期停在"开·未接管"。

修复三件事：

1. 主脚本在 `__xcIsLocalSkinUnowned` 之后暴露 `window.__xcLayaFacade = name => laya.class(name)`，复用 `__xcGetServerSkinDefault` 同一闭包里的 `laya`，不引入作用域风险；
2. 实例化处同时尝试直接传 `laya`（写成 `typeof laya === "undefined" ? undefined : laya`，即便该作用域取不到也不抛错）；
3. 模块 `runtime()` 依次取 `injectedLaya` → `window.__xcLayaFacade` → `window.laya / window.Laya`，此后所有查找都走它。

顺带补了两处健壮性：宿主解析结果可能是单元素数组（`holderOf` 会展开）；原型方法若被定义成不可写，改用 `defineProperty` 覆盖，仍失败则在 `lastFail` 写明「不可写」，不再静默。

诊断入口 `__xcNativeSkinLinkDiagnose()` 输出 `facade / facadeClass / calls / registry / scanned / lastFail`；按钮 title 也会附带 `lastFail`。

### 2.6 挂接点为什么必须落在类原型

首版把 `GetGeneralSkinIncludeHide` 包在 `laya.class("GeneralSkinManager")` 的返回对象上。若该方法构建的 `laya.class` 每次返回**新实例**，包装就会落在一个野对象上，而游戏内部用的是 `y8t.I()` 单例，于是开关显示"开"却毫无效果。

修复后 `pickHolder()` 由近到远定位真正持有该方法的对象：

1. `laya.class("GeneralSkinManager")` 返回类 → 取 `prototype`（实例尚未创建也能先挂上）
2. 返回实例 → 沿原型链找到首个 own descriptor（方法继承自原型时包原型，不污染实例）
3. 类上有 `I()` → 取单例
4. 全部失败 → `reflectHolder()` 扫描 `Laya.ClassUtils._classMap / __classMap / classMap`，按 `prototype.GetGeneralSkinIncludeHide` 反查
5. 仍未命中 → `scanHosts()` 从 `stage / gamescene / timer` 等存活对象出发，深度 4、上限 2500 节点做有界广度扫描

包原型的额外收益：新实例、单例、以及 mount 之后才创建的实例全部覆盖，消除了挂载时序竞争。

按钮文案同步改为三态：`关` / `开·已接管` / `开·未接管`，颜色分别为棕、绿、红。此前开关状态与挂接结果脱钩，用户看到"开"无法判断是否生效。

### 2.7 本地皮肤链路的作用

`localSkinSelections`（主脚本 38387 起）正好补在服务端这一环，两步：

1. `send()`：发请求前把 `closeSelectSkinId` 临时换成 `__xcGetServerSkinDefault(gid)` 的值（服务端认为的默认皮肤），`finally` 里恢复。**服务端永远只看到它认可的组合，不可能拒绝。**
2. `apply()`：回包到达（`SGSMODULE` 由 `base.js` 拦截 `console.log` 驱动）时，把 `entry.SkinID` 改回本地选择，`ServerProxy` 随后写库写到的就是跨版本值。

因此**只要本地皮肤链路在跑，服务端态度就不影响结果**。

**前提（关键）**：`record/send/apply` 只在 `runLocalSkinEnableInline()` 里装配，而它由「本地皮肤」开关触发（主脚本 38656），默认不启用。皮肤互通本身不含这段逻辑。

**代价**：`send()` 对**所有**选择都回传默认值，服务端记录的始终是默认皮肤，等价于"本机专属"，换设备/重装会回到默认。这也是它不能默认开启的原因。

## 3. 实现

新增四个非混淆模块，经 `scripts/build-userscript-modules.cjs` 装配：

- `src/features/native-skin-groups.js`：151 组同武将 ID 表（427 个武将 ID），从 `character.sgs` 生成
- `src/features/native-skin-labels.js`：427 个武将的显示名（`SpecifyName + name`，如 528 → 族吴苋），Tab 标题用
- `src/features/native-skin-link.js`：`createNativeSkinLink`，包装 `GetGeneralSkinIncludeHide`，并对其他模块开放 `wrap` / `withBucket`
- `src/features/native-skin-tabs.js`：`createNativeSkinTabs`，选肤窗口按版本分页

主脚本接线（2026-11-19 起不再有独立开关按钮）：

```js
const nativeSkinLink = createNativeSkinLink({ window, document, storage: localStorage,
  laya: typeof laya === "undefined" ? undefined : laya,
  groups: getNativeSkinGroups(),
  log: text => appendLocalSkinDebugLine("[皮肤互通] " + text, false) });
const nativeSkinTabs = createNativeSkinTabs({ window, document,
  laya: name => window.__xcLayaFacade?.(name),
  groups: getNativeSkinGroups(), labels: getNativeSkinLabels(),
  link: nativeSkinLink,
  log: text => appendLocalSkinDebugLine("[皮肤Tab] " + text, false) });
window.__xcNativeSkinLink = nativeSkinLink;
window.__xcNativeSkinTabs = nativeSkinTabs;
```

`runLocalSkinEnableInline()` 末尾调用 `nativeSkinTabs.attach()`：**开本地皮肤 = 开皮肤互通 + 选肤分页**。开关本身仍保持"开启后本会话锁定"的既有结构（历史上卸载本地皮肤出过问题）。

包装逻辑（幂等，可恢复）：

```js
const base = original.call(this, generalID, a, b, c);
if (!enabled) return base;
const row = groupOf(generalID);           // 名字/id 表
const out = Array.isArray(base) ? base.slice() : [];
for (peer of row 内其他 generalID) {
  const extra = original.call(this, peer, a, b, c);
  for (vo of extra) if (out.indexOf(vo) < 0) out.push(vo);
}
return out.length ? out : base;
```

- 参数（含隐藏皮肤、收藏、预售标记）原样透传给每个 peer，行为与原生一致
- 返回的是同一批 skinVO 引用，选肤窗口后续的 `sort(skinlevel1)`、去重、选中判断都不受影响
- 持有判断 `GetSkinListBySkinID` 不包装，未拥有仍然只是"未拥有"
- 关闭开关即时回退原生结果，不改方法；`dispose()` 才恢复描述符
- `laya.class` 可能返回单例或类，`pickManager()` 两种情况都处理；取不到时 500ms × 240 次有界重试
- 偏好 `localStorage.xcNativeSkinLink.v1` = `{ enabled: bool, off: [组名] }`，默认开启

### 3.1 选肤窗口多 Tab（2026-11-19，移除无效补挂）

本地皮肤开关启用互通与分页，不另设按钮；不涉及十周年。当前实现以真实开窗事件为入口，不再靠巡检修复窗口。

1. `attach()` 包装真正持有 `WindowManager.GetWindow` 的对象。原生该方法只创建/返回窗口，调用者随后才 `Show`；返回时用 `bindWindow` 安装该实例的 `enterWindow/destroy` 包装器。
2. 每次 `enterWindow(gid)` 在原生执行前 `startPage`，释放旧页、创建默认页和同组变体Tab，安装视图取数作用域。资源加载中没有selectView也无须等待：原生 `loadResComplete -> Init -> enterWindow` 自然到达同一入口。启用前已打开的窗口由一次GetWindowData只读检查初始化。
3. `initSkinListData/initSelectListData/RefreshShareSkin` 通过同步 `scopes` 栈限定当前页的GetOnlineSKinList。默认页保留官方GeneralSkinParent；变体页用withBucket读取所选ID的完整单桶，多个同名ID按skinID去重，空桶返回[]。窗口外查询仍是互通列表，武将实际realGeneralID/clientID不改。
4. 顶部Tab只在开窗创建。点击隔离输入后，在原精灵更新选中样式，在原pannel重画全部皮肤；不更换Tab对象、不发皮肤SET、不关窗，重置滚动和旧悬浮框。布局713×543、四列、列表y=84、横向溢出箭头；仅尺寸改变时initBg，避免重复触发原生resize/动画。
5. 分页视图/窗口calculateSize统一布局，不再走空列表关闭分支；列表刷新中的CLOSE和非选肤CLOSE被拦截。实际点击沿原生itemClick/composeSkinClick -> CLOSE -> Close -> AutoReclaim -> destroy -> closeSelectSure一次提交，既有localSkinSelections默认值隔离照常执行。右上角关闭及倒计时仍沿原生。

删除的逻辑：500ms巡检、5s心跳、2s扫树、挂载重试、GetWindow后0/300/900ms补挂、Show包装与300ms去重、healTabs/dropBars、80行日志缓存、首次列表延迟重建、Tab点击/销毁的0ms队列。它们不再参与运行；不把安装成功当作游戏内效果已验证。

职责与状态：createNativeSkinTabs拥有pages（每个窗口的列表页/Tab/滚动/恢复表）、windows（入口与销毁钩子）、scopes（同步取数栈）；mounted仅记录当前调试/API操作目标。nativeSkinLink拥有合并开关和单桶访问接口，原生视图及localSkinSelections拥有选肤/发送状态。view/window销毁释放所属页，detach停用包装层且不覆盖后装包装器，再恢复原生合并列表/尺寸；没有新增持久偏好和后台任务。ChangeSkinWindow（局内）、SelectSkinWindow（选将）及ModifyShowSkinWindow（展示）分别持有页，关闭/切换其中一个不会改另一个。

日志为 `[皮肤Tab] 分页已接入原生开窗入口 / 分页初始化（窗口、gid、页数） / 切页完成 / 选择皮肤 / 初始化或切页失败`，由既有appendLocalSkinTabDebugLine适配器归显式debug。状态接口仍为__xcSkinTabsStatus/__xcSkinTabsPlan；移除pendingMount/watching/mountTries等补挂字段，增加windowHooked。

测试夹具增加真实 `B9t.GetWindow`、`tTs.enterWindow`、`nqt.UpdateInfo/initUsingSKinID`、`xsi.loadResComplete`，仍使用同一OL明文SHA256。39组模拟通过；修改前在禁止分页定时器、稳定Tab对象、快速同将重开三项失败。首次资源异步/原生第一次渲染/无补挂重开均由实际摘录执行，尚未游戏内实测。

#### 3.1.1 局内皮肤选择器没有Tab：漏接ChangeSkinWindow

用户实测仍无Tab后，重新从按钮追到原生注册：`Ugs.onSKinClick@22057523` 从主/副将GeneralId/General2Id取ID，调用 `dt.I().A("ChangeSkinWindow", id)`；注册表是 `this.r("ChangeSkinWindow",ahs)`，ahs@21049773仍是当前局内窗口。此前“ahs是旧SelectSkinWindow实现”的判断错误；另外两个窗口各为SelectSkinWindow/tTs、ModifyShowSkinWindow/vps，并不能替代该入口。

修复仅在分页窗口名单补上ChangeSkinWindow，沿既有GetWindow -> enterWindow链执行；已打开时的GetWindowData一次初始化也包含它。首次页建立记录“分页初始化：窗口=ChangeSkinWindow gid=… 页数=…”，无新增后台补挂。夹具保存真实注册、ahs进入/尺寸方法、Ugs座位按钮，新增测试从实际按钮方法驱动，而不是把测试窗口固定叫SelectSkinWindow；旧代码第40组断言复现首次局内无Tab，修后42组通过，包括主副将、切Tab保留窗口、选肤一次提交、资源延迟和重开。此前39组仅证明既有两种窗口的模拟，不证明局内入口；本轮仍未游戏内实测。

#### 3.1.2 列表会变、选择后关窗但外观不变：新视图漏登记
