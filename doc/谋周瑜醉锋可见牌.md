## 官方客户端证据

1. `this.r("ZuiFeng", kei)` 注册醉锋。该快照的 `kei.GetResponser(t)` 仅在 `Type == IWi.OPT_SKILL_FLAG1` 时返回 `NQt`，`OPT_SKILL_FLAG1=28`；醉锋的 `SelectCardWindowServer` 为真。
2. `NQt.Response(t)` 将 `t.TargetSeatID` 对应的座位和 `t.Params` 交给 `SelectCardWindow`。协议 getter `TargetSeatID` 返回实际字段 `targetSeatID`；`SeatID` 是操作座位，`SrcSeatID` 是技能来源，不能把目标手牌写到这两个座位。
3. `SelectCardWindow` 注册到该快照的 `als`。`enterWindow(t)` 在 `Skill.SelectCardWindowServer` 分支逐项将 `t.Params[i]` 传给 `L$t.GetInstance`，再创建手牌 UI。因此这条消息的 `Params` 是牌号列表，没有头部计数、花色掩码或座位字段需要剥离。
4. `GsCRoleOptTargetNtf` 注册类为该快照的 `IWi`，新协议映射为 `108020`、旧协议表为 `21215`。反序列化得到 `SeatID/targetSeatID/SrcSeatID/SpellID/Type/Param/Params`；protobuf 适配的 `datas` 最终也写入 `Params`。
5. 醉锋的 `UpdateRoleDataResponse` 则把 `Datas[0]/Datas[1]` 解释为 `usedSuitMask/lockedSuitMask`。这些是花色位掩码，不能作为可见牌号接入。

上述混淆类符号只用于本次快照定位，不作为 userscript 的运行依赖。

## 接入链与限制

`SGSMODULE -> main -> logic -> GsCRoleOptTargetNtf(SpellID=4025, Type=28) -> new Zone(targetSeatID).show(Params) -> Zone.draw/flushRender -> 主记牌面板与座位旁副本`。

- 仅接收 `isSend` 非真、`Type=28`、目标座位为整数且在 `0..254`、`Params` 为数组，并且 `Card.key` 已初始化的消息。座位 `0` 有效，`255` 是非玩家区域，不能写成目标手牌。
- 对 `Params` 取正整数并去重，不修改原消息；隐藏占位 `0`、负数、字符串、空值等不记录为牌。未被揭示的手牌槽位仍保持未知。
- 数据写入现有 `Zone.obj["5-"+targetSeatID]`，由 `Card.identify/Zone.show` 维护已知状态；没有新增技能缓存、配置开关、会员条件或模式白名单。普通 OL 消息和既有牌集初始化仍是前提。
- 随后的公开展示与用酒/弃置继续交给 `PubGsCMoveCard`：同区展示不重复加牌，实际移走时从可见手牌删除。`PubGsCUseCard` 通知本身不抢先扣牌。
- 接入的是本客户端实际收到的牌号；不会根据技能说明推算未下发的手牌，也不会把技能状态 `Datas`、其它 `Type` 或顾曲标记当作醉锋选牌列表。
- 调试开启时，`stepVisibleCardTrace` 记录 `zuifeng:reveal` 或 `zuifeng:skip`，随后有 `show:before/after`、`event:done`、`render:after`；日志通过现有桥最终进入 `appendLocalSkinDebugLine()`，关闭调试不影响记牌。
